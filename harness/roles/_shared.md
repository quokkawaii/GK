# 공통 역할 실행 계약

이 파일은 모든 역할이 읽는 공통 계약이다. 역할별 파일은 이 계약을 보완하며, 충돌하면 `AGENTS.md`와 사용자 지시가 우선한다.

## 1. 역할 시작 체크

작업을 시작하기 전에 아래 네 가지를 확인한다.

1. 현재 단계와 다음 단계의 사용자 승인이 무엇인지 확인한다.
2. 자신의 역할에 필요한 입력 문서와 결정이 승인됐는지 확인한다.
3. 작업 대상 파일·폴더와 수정 권한을 명확히 확인한다.
4. 작업 결과가 어떤 역할에게 인계될지 확인한다.

하나라도 없으면 새 산출물을 만들지 않는다. 필요한 정보를 한 번에 하나씩 사용자에게 질문하거나, 현재 산출물의 빈 항목을 `[TBD-번호]`로 표시한다.

## 2. 권한과 경계

- 자신의 역할 산출물만 작성·수정한다. 타 역할의 확정 요구사항·결정·리뷰 기록을 임의로 바꾸지 않는다.
- 사용자 승인 전에는 앱 코드, 의존성, 데이터베이스, API, 배포 환경을 만들거나 변경하지 않는다.
- 새 폴더를 만들 때는 목적·경로·생성 파일을 먼저 알리고 승인받는다. 사용자가 특정 역할 파일 생성을 명시적으로 요청한 경우만 그 범위에서 예외다.
- 사실, 숫자, 회사 정보, 제품 사양은 근거 없이 작성하지 않는다.
- 중요 항목에는 `REQ-`, `DEC-`, `TBD-` 식별자를 사용한다. 리뷰 이슈는 `PLAN-REV-`, `DESIGN-REV-`, `DEV-REV-` 식별자를 사용한다.

## 3. 공통 작업 방식

- 요청을 받으면 먼저 `목표 → 입력 → 작업 범위 → 완료 기준`을 짧게 확인한다.
- 인터뷰·질문·설명에서는 내부 구현 용어로 사용자의 판단을 추상화하지 않는다. 현재 화면·콘텐츠·선택지를 구체적으로 제시하고, 사용자가 결정해야 할 결과를 평이한 말로 묻는다.
- 결과물에는 독자가 다음 행동을 알 수 있도록 목적, 결정 사항, 미확정 사항을 구분한다.
- 전체 재작성보다 필요한 항목만 수정한다. 변경 시 무엇을 왜 바꿨는지 간단히 남긴다.
- 의견 충돌은 해결하지 않는다. 쟁점, 관련 ID, 선택지, 이득·비용, 추천안을 제시하고 사용자 결정을 기다린다.

## 4. 인계 형식

각 역할은 종료 전에 아래 항목을 남긴다.

```md
## 인계
- 완료: [완료한 산출물 또는 REQ ID]
- 확정: [사용자 승인 또는 DEC ID]
- 미확정: [TBD ID와 질문]
- 다음 역할 입력: [파일 또는 결정]
- 다음 행동: [승인을 받아야 하는 한 가지 행동]
```

## 5. 품질과 실패 처리

- 검증 도구가 이미 있는 경우에만 실행한다. 없는 도구를 임의로 만들지 않는다.
- 같은 오류에 대해 두 번의 실질적 수정 시도 후에도 막히면, 시도와 오류를 사용자에게 보고한다.
- 결과가 불명확하면 완료라고 선언하지 않는다.

## 6. 패치 변경 보고

파일을 추가·수정·삭제·이동한 역할은 적용 직후 `harness/patch-notes/YY-MM-DD.md`에 아래 형식으로 보고한다. 같은 날짜에는 기존 파일 끝에 추가한다.

```md
## 변경 N — 역할명
- 행동: 수정
- 파일: `상대/경로/파일명`
- 내용: 무엇을 어느 범위에서 바꿨는지
- 이유: 사용자 요청, REQ·DEC·REV 또는 오류 근거
- 관련: REQ-001 / DEC-001 (없으면 `없음`)
- 검증: 실행한 검증 또는 `문서 변경으로 검증 대상 없음`
```

- 여러 파일을 바꾸면 파일별로 항목을 나눈다.
- 보고 파일은 사실을 추가하는 용도이며, 과거 기록을 조용히 고치거나 지우지 않는다. 정정이 필요하면 새 항목으로 남긴다.
- `harness/patch-notes/` 자체를 갱신한 행위는 다시 보고하지 않는다.
