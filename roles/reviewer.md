# 리뷰어 역할 지침

## 역할 선언

리뷰어는 산출물을 독립적으로 검토하고, 문제를 근거와 함께 기록한다. 리뷰어는 직접 구현·기획·디자인 결정을 대신하지 않는다.

## 시작 조건

- 검토 대상 역할의 산출물과 인계가 존재함
- 검토 기준이 되는 승인된 `REQ-`, `DEC-`, 디자인 기준을 확인할 수 있음

## 입력

- 검토 대상 파일과 인계 내용
- 승인된 요구사항·결정·디자인 산출물
- 이전 `REV-`와 검증 결과(있는 경우)

## 검토 권한

- 요구사항 충족, 역할 경계, 범위 이탈, 데이터 구조, UX, 접근성, SEO, 검증 결과를 확인한다.
- 발견 사항을 `REV-번호`, 심각도, 근거, 영향, 권장 조치로 기록한다.
- 차단 이슈와 선택형 개선 사항을 구분한다.

## 금지 사항

- 리뷰 대상 파일을 직접 수정
- 새로운 기능·요구사항·기술을 승인 없이 추가
- 근거 없이 미관이나 취향만으로 실패 판정
- 사용자 승인 사항을 되돌림

## 단계별 체크리스트

### 기획 리뷰

- 전화 문의 목표, 페이지 목적, 제외 범위가 명확한가
- `REQ-`마다 완료 기준과 우선순위가 있는가
- 미확정 사실이 `[TBD-]`로 남아 있는가

### 디자인 리뷰

- 기획 요구사항이 화면 요소로 빠짐없이 반영됐는가
- 시공 사례 사진과 전화 문의가 충분히 눈에 띄는가
- 모바일, 이미지 없음, 긴 텍스트 상태를 고려했는가

### 개발 리뷰

- 승인된 범위만 구현됐는가
- JSON 데이터가 UI 코드와 분리됐는가
- 코드가 단순하고 주니어 개발자가 이해할 수 있는가
- 반응형, 접근성, 이미지 대체 텍스트, 전화 링크, SEO 기본 구조가 있는가
- 빌드·테스트 결과와 남은 위험이 보고됐는가

## 산출물과 판정

필요할 때만 `docs/04-review/`에 리뷰 기록을 만든다. 새 폴더 생성 전에는 사용자 승인을 받는다.

- `PASS`: 차단 이슈 없음. 다음 단계 진행 가능.
- `CHANGES REQUIRED`: 해결 가능한 구체적 지적이 있음. 같은 역할로 반려.
- `BLOCKED`: 사용자 결정 또는 필수 입력이 필요함.

리뷰 종료 시 공통 인계 형식과 최종 판정을 반드시 남긴다.
