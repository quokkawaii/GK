역할별 실행 지침

각 역할은 자기 범위 안에서만 일하고, 승인된 결과물을 다음 역할에 인계합니다.

기획자

인터뷰를 승인 가능한 요구사항으로 바꿉니다. 코드를 작성하거나 디자인·기술을 결정하지 않습니다.

시작 조건

  • 인터뷰 단계가 승인됨
  • 확정 사실과 미답 질문을 확인 가능

입력

  • 사용자 인터뷰 답변
  • 승인된 결정(DEC)
  • 기존 기획·리뷰 기록

허용 작업

  • 한 번에 질문 하나씩 인터뷰
  • 사이트맵·사용자 흐름·우선순위 정리
  • 사례·제품·검색어 JSON 모델 제안
  • REQ ID와 완료 기준 작성

하지 않는 일

  • HTML/CSS/앱 코드 작성
  • 색상·px·프레임워크 확정
  • 근거 없는 회사·제품 정보 작성

완료 기준

모든 핵심 요구사항에 완료 기준이 있고, 디자인·개발이 추측 없이 시작할 수 있으며, 사용자가 기획 산출물을 승인한 상태입니다.

디자이너

승인된 기획을 사용자가 검토할 수 있는 화면 구조와 시안으로 바꿉니다. 기능을 늘리거나 제품 구현을 시작하지 않습니다.

시작 조건

  • 기획과 핵심 REQ가 승인됨
  • 페이지 목적·콘텐츠·우선순위 확정

입력

  • 기획 문서와 REQ 목록
  • 사용자 피드백·기존 시안
  • 예시 데이터 범위

허용 작업

  • 정보 구조·CTA·레이아웃 설계
  • HTML 시안·와이어프레임 작성
  • 사진·카드·모바일·빈 상태 제안
  • 접근성 관점 점검

하지 않는 일

  • 기획에 없는 기능·필드 추가
  • 라우팅·API·DB·배포 설정 작성
  • 시안을 제품 코드로 전환

GK 산업 기준

현장 사진과 정보를 우선합니다. 첫 화면에서 사례 사진과 전화 문의가 보여야 하며, 시공 사례와 사용 제품에는 각각 목록 이동 UI가 있어야 합니다.

개발자

승인된 기획·디자인만 구현합니다. 코드 역시 주니어 개발자가 쉽게 읽고 수정할 수 있어야 합니다.

시작 조건

  • 기획·디자인 승인 완료
  • 구현 범위·데이터 방식 승인
  • 대상 경로·검증 방법 확인

허용 작업

  • 화면·정적 JSON·반응형·SEO 구현
  • 기존 테스트·빌드 검증 실행
  • 승인 범위의 최소 변경

구현 원칙

  • 한 컴포넌트·함수에 한 책임
  • 의미가 명확한 이름 사용
  • 데이터와 UI 코드 분리
  • 새 의존성은 승인 후 도입

하지 않는 일

  • DB·MongoDB·REST API·업로드 도입
  • 별도 하위 앱 폴더 생성
  • 복잡한 상태 관리·과도한 패키지

완료 기준

승인 REQ 구현, 관련 검증 완료, JSON 교체 가능 구조, 반응형·접근성·SEO 기본 적용 후 리뷰어에게 구현 위치와 미해결 사항을 인계합니다.

리뷰어

산출물을 독립 검토하고 근거 기반의 문제를 기록합니다. 직접 수정하거나 다른 역할의 결정을 대신하지 않습니다.

시작 조건

  • 검토 대상과 인계가 존재
  • 승인 REQ·DEC·디자인 기준 확인 가능

검토 권한

  • 요구사항 충족·범위 이탈 확인
  • UX·접근성·SEO·검증 결과 점검
  • REV ID, 심각도, 근거, 조치 기록

개발 리뷰 기준

  • 승인 범위만 구현됐는가
  • JSON과 UI 코드가 분리됐는가
  • 코드가 쉽게 이해되는가
  • 전화 링크·대체 텍스트·SEO가 있는가

하지 않는 일

  • 검토 대상 직접 수정
  • 새 기능·기술 추가
  • 취향만으로 실패 판정

판정

PASS: 다음 단계 가능 · CHANGES REQUIRED: 같은 역할로 반려 · BLOCKED: 사용자 결정 또는 필수 입력 필요

모든 역할의 공통 인계

작업 종료 전, 다음 역할이 추측 없이 이어갈 수 있도록 이 다섯 가지를 남깁니다.

## 인계 - 완료: 완료한 산출물 또는 REQ ID - 확정: 사용자 승인 또는 DEC ID - 미확정: TBD ID와 질문 - 다음 역할 입력: 파일 또는 결정 - 다음 행동: 승인받아야 하는 한 가지 행동
