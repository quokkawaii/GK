# 구현 계획 결정 기록

## DEC-011 — 프런트엔드와 배포 방식

- 결정: Next.js와 TypeScript로 구현하고, 서버·DB 없이 정적 결과물을 배포한다.
- 이유: 이 서비스는 전화 문의 중심의 소개 사이트이며, 정적 JSON 데이터와 페이지별 검색 노출이 필요하다.
- 영향: REST API, 데이터베이스, 인증, 업로드 기능은 도입하지 않는다. 콘텐츠 변경 후에는 다시 빌드·배포한다.
- 상태: 확정
- 최종 확인: 2026-08-08 구현 계획 검토 인터뷰에서 사용자가 이 기술 방향을 다시 승인했다.

## DEC-012 — 이미지 파일과 경로 관리

- 결정: 실제 사진은 `public/images/` 아래에 저장하고, 사례·제품 JSON에는 `/images/...` 형식의 경로 문자열만 저장한다.
- 예시: `public/images/cases/case-001/01.jpg` → JSON의 `"/images/cases/case-001/01.jpg"`
- 이유: 사진 교체와 사례·제품 데이터 수정을 분리해 관리하고, 정적 배포 환경에서 단순하게 제공하기 위함이다.
- 상태: 확정
- 최종 확인: 2026-08-08 구현 계획 검토 인터뷰에서 사용자가 이 사진 관리 방식을 다시 승인했다.

## DEC-013 — 콘텐츠 JSON 폴더

- 결정: JSON 파일은 `data/` 대신 프로젝트 루트의 `content/` 폴더에서 용도별로 관리한다.
- 구성: `cases.json`, `site.json`. 사용 제품 목록은 `cases.json`의 `productIds`에서 만들고, SEO 기본 검색어는 `site.json`의 `keywords`에서 관리한다.
- 이유: 이 파일들은 개발용 데이터가 아니라 사이트에 표시할 콘텐츠이므로, 비개발자도 의미를 이해하기 쉬운 이름을 사용한다.
- 상태: 확정
- 최종 확인: 2026-08-08 구현 계획 검토 인터뷰에서 사용자가 이 JSON 콘텐츠 관리 방식을 다시 승인했다.

## DEC-014 — 시공 사례 상세 주소

- 결정: 시공 사례 상세 주소는 고유 번호와 읽기 쉬운 이름을 결합한다.
- 형식: `/cases/case-001-hwaseong-factory-epoxy`
- JSON: 내부 식별자 `id`와 주소용 `slug`를 함께 관리한다.
- 이유: 사례명이나 공법이 같아져도 고유 번호로 주소 중복을 막고, 주소만 보아도 사례 내용을 짐작할 수 있게 하기 위함이다.
- 상태: DEC-085로 대체

## DEC-015 — 시공 사례 대표 이미지

- 결정: 시공 사례 JSON에 목록·웰컴 페이지용 대표 사진의 위치를 `thumbnailIndex` 숫자로 둔다.
- 형식: `"thumbnailIndex": 0` → 화면에서는 `images[thumbnailIndex]`를 사용한다.
- 규칙: 이미지 경로와 대체 텍스트는 `images` 배열에서 한 번만 관리한다.
- 이유: 대표 이미지 경로를 중복 저장하지 않고, 목록·웰컴 페이지와 상세 사진이 같은 이미지 정보를 재사용하게 하기 위함이다.
- 상태: 확정

## DEC-016 — 화면 주소 구조

- 결정: Next.js 라우팅 주소를 화면 역할별로 단순하게 관리한다.
- 주소:
  - `/` — 웰컴 페이지
  - `/cases` — 시공 사례 목록
  - `/cases/case-001-hwaseong-factory-epoxy` — 시공 사례 상세
  - `/products` — 사용 제품 목록
  - `/company` — 회사 소개
- 이유: 사용자가 React/Next 라우팅 주소의 의미를 확인했고, 사례·제품·회사 소개를 읽기 쉬운 단순 주소로 관리하기로 했다.
- 상태: 사례 상세 주소 부분은 DEC-085로 대체

## DEC-017 — 목록 상태 관리

- 결정: 첫 클라이언트 진입 때 `cases.json`과 `site.json` 내용을 Zustand 콘텐츠 스토어에 한 번 초기화한다. 이후 화면은 Zustand 선택기로 필요한 사례·사이트 정보만 읽는다.
- 저장: 콘텐츠 데이터는 `sessionStorage`에 저장하지 않고 메모리에만 둔다. 필터와 페이징은 서로 다른 Zustand 스토어·저장소로, 사용자가 현재 열어 둔 이 사이트의 브라우저 탭 안에서만 유지한다.
- 페이지 규칙: 필터를 선택·해제하거나 사용 제품 카드에서 자재 필터를 적용해 사례 목록으로 이동하면 페이지 번호를 `0`으로 초기화한다. 고객 화면에는 `pageNumber + 1`을 표시한다.
- 범위: 콘텐츠 스토어는 사례와 공통 사이트 정보, 필터 스토어는 선택 태그, 페이징 스토어는 `pageNumber`를 관리한다. 페이지 크기는 상수에서 가져온다. URL 쿼리와 서버·엔드포인트 상태 연동은 초기 범위에서 제외한다.
- 이유: JSON을 페이지·컴포넌트마다 반복해 읽거나 정리하지 않고, 사용자에게 필요한 데이터만 전역 상태에서 표시하기 위함이다.
- 상태: 확정
- 최종 확인: 2026-08-08 구현 계획 검토 인터뷰에서 사용자가 Zustand·sessionStorage 사용과 URL 쿼리 미사용을 다시 승인했다.

## DEC-078 — Zustand 콘텐츠 초기화

- 처리: `store/contentStore.ts`가 `cases.json`과 `site.json`을 한 번 가져와 Zustand 콘텐츠 스토어의 초기값으로 둔다. 브라우저에서 이 모듈이 처음 실행될 때 사례 배열과 사이트 정보가 전역 콘텐츠 상태가 된다.
- 사용: 화면은 `useContentStore((state) => state.cases)`처럼 선택기로 값을 읽는다. 사례 목록을 다시 만들기 위한 JSON 파싱·정제 함수는 페이지마다 실행하지 않는다.
- 제외: 실제 사진 파일은 스토어에 넣지 않는다. JSON의 이미지 경로와 대체 텍스트만 저장하고, 사진은 화면 카드·갤러리가 표시할 때 브라우저가 불러온다.
- 상태: 확정

## DEC-079 — 필터·페이징 상태 분리

- 필터 저장소: `gk-case-filter`에는 `selectedTags`만 저장한다. `toggleTag`, `replaceSelectedTags`, `clearSelectedTags`가 이 값만 변경한다.
- 페이징 저장소: `gk-case-pagination`에는 `pageNumber`만 저장한다. 초기값은 `INITIAL_PAGE_NUMBER`인 `0`이며, `setPageNumber`, `resetPageNumber`가 이 값만 변경한다. `pageSize`는 `CASES_PER_PAGE` 상수에서 가져온다.
- 계산값: `totalElements`, `totalPages`, `hasPrevious`, `hasNext`, `numberOfElements`, `empty`는 현재 필터 결과와 `CASES_PER_PAGE`에서 매번 계산하며 저장하지 않는다. 저장하면 콘텐츠 변경 뒤에 오래된 값이 남을 수 있기 때문이다.
- 목록 요청 형태: 실제 API는 아직 만들지 않지만, 화면 내부에서는 `selectedTags`, `pageNumber`, `pageSize`, 고정 정렬 기준(ID 내림차순)을 합친 목록 조회 조건을 사용한다. 이후 API가 필요해져도 같은 구조를 확장할 수 있다.
- 연동: 필터 변경을 처리하는 `handleCaseFilterChange`는 필터 저장소를 바꾸고 페이징 저장소의 `pageNumber`를 `0`으로 되돌린다.
- 상태: 확정

## DEC-080 — JPA Page 형태를 따른 사례 JSON

- 결정: `cases.json`의 루트는 사례 배열 `content`만 둔다. 고정된 페이지 기본값은 JSON이 아닌 상수 파일에 둔다.
- 기준: `INITIAL_PAGE_NUMBER = 0`, `CASES_PER_PAGE = 4`를 `lib/constants.ts`에 둔다. 고객 화면에서는 항상 `pageNumber + 1`을 표시한다.
- 결과: 사례 조회 함수는 필터·ID 내림차순 정렬·페이징을 적용한 뒤 `content`, `pageable`, `totalElements`, `totalPages`, `hasPrevious`, `hasNext`, `numberOfElements`, `empty`를 반환한다. 이 결과값은 JSON에 고정 저장하지 않는다.
- 이유: JPA 페이징과 같은 데이터 흐름으로 함수를 만들되, 정적 JSON의 필터 결과가 바뀔 때마다 전체 건수와 페이지 수가 어긋나는 문제를 막기 위해서다.
- 상태: 확정

## DEC-020 — 줄 바꿈 방식

- 결정: 프로젝트의 줄 바꿈 방식은 LF로 통일한다.
- 적용: 개발 단계에서 Prettier의 `endOfLine` 및 Git 관련 설정을 LF 기준으로 맞춘다.
- 이유: 운영체제가 달라 줄 바꿈만 변경된 것처럼 보이는 Git 변경을 줄이기 위함이다.
- 상태: 확정

## DEC-021 — 들여쓰기

- 결정: 들여쓰기는 탭 문자 대신 공백 2칸으로 통일한다.
- 적용: 개발 단계에서 Prettier의 `tabWidth`를 `2`, `useTabs`를 `false`로 설정한다.
- 이유: VS Code를 포함한 편집기 설정이 달라도 저장되는 코드 모양을 일정하게 유지하기 위함이다.
- 상태: 확정

## DEC-022 — 한 줄 최대 길이

- 결정: 코드 한 줄의 최대 길이는 100자로 통일한다.
- 적용: 개발 단계에서 Prettier의 `printWidth`를 `100`으로 설정한다.
- 이유: 긴 코드를 읽기 쉽게 나누되, 불필요하게 많은 줄 바꿈이 생기는 것을 피하기 위함이다.
- 상태: 확정

## DEC-023 — 세미콜론 사용

- 결정: JavaScript·TypeScript 코드 문장 끝에는 세미콜론을 항상 사용한다.
- 적용: 개발 단계에서 Prettier의 `semi`를 `true`로 설정한다.
- 이유: 문장 경계를 명확히 하고, 자동 서식 결과를 예측 가능하게 유지하기 위함이다.
- 상태: 확정

## DEC-024 — 문자열 따옴표

- 결정: JavaScript·TypeScript 문자열은 큰따옴표(`"`)로 통일한다.
- 적용: 개발 단계에서 Prettier의 `singleQuote`를 `false`로 설정한다.
- 이유: 사용자가 Java에서 사용하던 문자·문장 구분 방식에 맞춰 스크립트 문자열을 큰따옴표로 통일하기로 했다.
- 상태: 확정

## DEC-025 — 마지막 쉼표

- 결정: 여러 줄로 작성한 배열·객체·함수 인자의 마지막 항목 뒤에는 쉼표를 항상 사용한다.
- 적용: 개발 단계에서 Prettier의 `trailingComma`를 `all`로 설정한다.
- 이유: 항목을 추가하거나 삭제할 때 필요한 Git 변경 범위를 작게 유지하기 위함이다.
- 상태: 확정

## DEC-026 — 개발 폴더 구조와 디자인 시스템 위치

- 최종 확인: 2026-08-08 구현 계획 검토 인터뷰에서 사용자가 기존 확정 구조의 사용을 다시 승인했다.

## DEC-027 — 커밋 전 코드 검사

- 결정: Git 커밋 직전에 변경한 코드만 ESLint 검사와 Prettier 서식 검사를 자동 실행한다.
- 도구: 개발 단계에서 Husky와 lint-staged를 사용한다.
- 이유: 공통 코드 규칙과 다른 파일이 GitHub에 올라가는 것을 막고, 전체 프로젝트를 매번 검사하지 않아 커밋을 빠르게 유지하기 위함이다.
- 상태: 확정

## DEC-028 — 자동 테스트와 실패 대응

- 결정: 태그 필터·페이지 계산처럼 결과를 명확히 확인할 수 있는 핵심 데이터 규칙에 자동 테스트를 사용한다.
- 실패 대응: 테스트에서 문제가 발견되면 개발자는 문제 내용, 영향, 예정 조치를 사용자에게 보고하고 승인받기 전에는 수정하지 않는다.
- 금지: 테스트 실패를 해결하기 위한 코드 작성·테스트 실행의 반복을 사용자 승인 없이 진행하지 않는다.
- 이유: 자동 테스트는 품질 확인에 사용하되, 요구사항이나 수정 범위의 판단은 사용자가 통제하도록 하기 위함이다.
- 상태: 확정

## DEC-029 — 자동 테스트 도구

- 결정: 핵심 데이터 규칙의 자동 테스트 도구로 Vitest를 사용한다.
- 적용: 개발 단계에서 Vitest를 설치하고, 첫 필터 규칙 테스트를 작성해 사용자가 실제 실행 결과를 확인할 수 있게 한다.
- 변경: 사용자가 필요 없거나 맞지 않다고 판단하면 Vitest와 관련 설정·테스트 파일을 별도 승인 후 제거할 수 있다.
- 이유: 사용자가 우선 실제로 사용해 본 뒤 유지 여부를 판단하기로 했다.
- 상태: 확정

## DEC-030 — 사진 표시 방식

- 결정: 시공·제품 사진은 Next.js의 `Image` 기능으로 표시한다.
- 적용: 정적 배포 환경에 맞춰 서버 이미지 변환은 사용하지 않고, `public/images/`의 사진 경로를 그대로 사용한다. 모든 사진에는 의미 있는 대체 문구를 둔다.
- 기대 효과: 사진 크기를 미리 잡아 화면 흔들림을 줄이고, 화면 아래 사진은 필요한 시점에 불러와 초기 로딩을 가볍게 한다.
- 이유: 사용자가 Next.js Image 기능 사용을 승인했다.

## DEC-031 — JSON 기반 시공 사례 상세 페이지 생성

- 이유: 사용자가 404 외의 오류와 주소 이동 가능성까지 대비하도록 요청했다.

## DEC-081 — 사례 조회·상태 보정 흐름

- 조회: `getCasePage`는 ① 모든 선택 태그를 가진 사례만 필터링하고 ② `id DESC`로 정렬하고 ③ 전체 건수·전체 페이지를 계산한 뒤 ④ `pageNumber * CASES_PER_PAGE`부터 `CASES_PER_PAGE`개를 잘라 반환한다.
- 반환: `CasePage`에는 `content`, `pageable`, `totalElements`, `totalPages`, `hasPrevious`, `hasNext`, `numberOfElements`, `empty`가 있다. 목록 화면과 페이지 번호 컴포넌트는 이 반환값만 사용한다.

- 사용: `contentStore`는 `cases.json`, `site.json`을 `import`로 가져와 초기 콘텐츠 상태로 사용한다.
- 범위: 이 설정은 JSON 파일을 TypeScript에서 가져오고 필드 이름 실수를 빌드 전에 확인하는 용도다. 사례 ID 중복, 필수값 같은 콘텐츠 규칙 검사는 별도 `check:content`가 담당한다.
- 적용 시점: Next.js 프로젝트 설정 파일을 만드는 개발 단계에서 적용한다.
- 상태: 확정

## DEC-083 — 저장 상태 버전 관리 제외

- 결정: 현재 열어 둔 이 사이트의 브라우저 탭에 저장하는 필터·페이징 상태에 별도 버전 번호나 이전 저장값 변환 기능을 추가하지 않는다.
- 처리: 콘텐츠가 바뀐 뒤 남은 태그·페이지 값은 `normalizeCaseListState`가 현재 데이터 기준으로 보정한다.
- 이유: 현재 정적 사이트 규모에서는 저장 구조 변경을 위한 별도 시스템보다 단순한 상태 보정이 적절하기 때문이다.
- 상태: 확정

## DEC-085 — 사례 상세 팝업과 개별 주소 제거

- 결정: 시공 사례 카드를 누르면 `/cases/[id]` 같은 별도 주소로 이동하지 않고, 현재 목록 화면 위에 상세 팝업을 띄운다.
- 상태: 선택된 사례는 `selectedCaseId: number | null`로만 관리한다. 카드는 사례 객체의 `id`를 직접 전달해 팝업을 열고, 닫기 버튼 또는 팝업 바깥 영역 클릭은 `selectedCaseId`를 `null`로 바꾼다. 이 값은 브라우저 탭 저장소에 저장하지 않는다.
- 영향: 사례별 정적 페이지 생성, 사례 상세 주소, 사례 상세 전용 404 처리는 만들지 않는다. 기존 DEC-014, DEC-016의 사례 상세 주소 부분, DEC-031, DEC-033의 사례 상세 주소 부분을 대체한다.
- 상태: 확정

## DEC-084 — 페이지 번호 묶음과 이전 버튼

- 페이지 번호: `PAGE_BUTTON_COUNT = 5`를 사용해 5개씩 표시한다. 내부 `pageNumber` 기준으로 `0~4`, `5~9`처럼 묶고, 고객 화면에는 각각 `1~5`, `6~10`으로 표시한다.
- 이전 버튼: 현재 `pageNumber`가 `0`이면 이전 페이지 버튼을 표시하지 않는다. `pageNumber`가 `1` 이상이면 표시하고, 누르면 `pageNumber - 1`로 이동한다.
- 계산: `getCasePage`의 `hasPrevious`는 `pageNumber > 0`일 때 `true`로 반환한다. 페이지 번호 UI는 이 값으로 이전 버튼 표시 여부를 결정한다.
- 번호 함수: `getVisiblePageNumbers(pageNumber, totalPages)`가 현재 묶음의 내부 페이지 번호 배열을 반환한다. 화면은 각 값에 `1`을 더해 표시한다.
- 다음 버튼: 현재 페이지가 마지막 페이지이면 다음 페이지 버튼을 표시하지 않는다. 마지막 페이지보다 앞에 있을 때만 표시하고, 누르면 `pageNumber + 1`로 이동한다. `getCasePage`의 `hasNext` 값으로 표시 여부를 결정한다.
- 상태: 확정

## DEC-077 — 공통 사이트 정보 JSON

- 결정: 회사명, 대표 전화번호, 활동 지역, 회사 소개, 외부 채널 주소, SEO 기본 검색어는 `content/site.json`에서 관리한다.
- 값: 주소·사업자 정보·외부 채널 URL처럼 아직 확정되지 않은 값은 `null`로 둔다. 외부 채널 URL이 `null`인 경우 화면에는 `준비 중`만 표시하며 링크를 만들지 않는다.
- 이유: 페이지와 컴포넌트에 공통 정보를 반복 작성하지 않고, 실제 정보가 준비되면 한 파일에서 교체하기 위해서다.
- 상태: 확정
