# 자동 테스트 정책

## 적용 범위

- 태그 다중 선택 시 선택한 태그를 **모두** 가진 사례만 표시하는 규칙
- 필터 초기화 규칙
- 페이지 번호와 페이지당 4개 카드의 계산 규칙
- JSON 데이터에서 대표 사진을 선택하는 규칙
- 숫자 ID 내림차순으로 시공 사례가 먼저 오는 정렬 규칙
- 제품 카드의 `시공 사례 보기`가 선택 자재 태그를 사례 필터에 설정하는 규칙
- 필터 변경 또는 제품 카드의 사례 이동 시 목록 페이지 번호를 1로 초기화하는 규칙

화면의 색, 간격, 사진 크기 같은 디자인 결과는 자동 테스트 대신 승인된 HTML 시안과 직접 확인으로 검토한다.

## 상세 팝업 수동 접근성 확인

브라우저 동작과 키보드 초점은 Node 기반 자동 테스트 범위에 넣지 않는다. 개발자가 실제 화면에서 아래 항목을 확인한다.

- 사례 카드 전체를 키보드로 열 수 있는지
- 팝업을 열면 첫 조작 요소로 초점이 이동하는지
- 팝업이 열린 동안 `Tab`·`Shift + Tab` 이동이 팝업 안에서 순환하는지
- 닫기·팝업 바깥 클릭·PC의 `Esc`가 동작하는지
- 닫은 뒤 처음 열었던 사례 카드로 초점이 돌아오는지
- 사진 확대 뷰어를 닫으면 상세 팝업으로 돌아오는지

## 도구

- Vitest를 사용한다.
- 초기 테스트 실행 환경은 기본 Node 환경으로 둔다. 브라우저 모사 환경은 실제 화면 자동 테스트가 필요해질 때 별도 승인 후 추가한다.
- 테스트 파일은 제품 코드와 분리된 `tests/` 폴더에 두며, 대상 폴더 구조를 따른다. 예: `tests/lib/filterCases.test.ts`.
- 개발 단계에서 첫 테스트를 추가할 때 실제 실행 방법과 통과·실패 결과를 사용자에게 함께 보여준다.
- 사용자가 필요 없거나 맞지 않다고 판단하면, 관련 설정과 테스트 파일을 별도 승인 후 제거한다.

## 실행과 실패 처리

1. 개발자가 승인된 범위의 코드를 작성한다.
2. 자동 테스트를 실행한다.
3. 통과하면 결과를 변경 보고에 기록한다.
4. 실패하면 **수정하지 않고** 아래 내용을 사용자에게 먼저 보고한다.
   - 실패한 테스트와 실제 결과
   - 사용자 화면 또는 데이터에 미치는 영향
   - 원인 추정
   - 수정하려는 파일과 조치 계획
5. 사용자가 승인한 뒤에만 수정하고, 수정 후 테스트를 다시 실행한다.

## 금지 사항

- 테스트가 통과할 때까지 사용자 승인 없이 코드 수정과 테스트 실행을 반복하지 않는다.
- 테스트를 통과시키기 위해 요구사항을 임의로 낮추거나 테스트를 삭제·무시하지 않는다.
