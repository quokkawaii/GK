# requirements 폴더 구조

```text
requirements
├─ AGENTS.md
├─ 01-common-req.md          # 전역 또는 둘 이상의 페이지에 공유되는 요구사항
├─ 02-home-req.md            # 홈 전용 요구사항
├─ 03-cases-req.md           # 시공 사례 전용 요구사항
├─ 04-products-req.md        # 제품 소개 전용 요구사항
└─ 05-about-req.md           # 회사 소개 전용 요구사항
```

- 요구사항은 공통 또는 실제 적용 페이지에 따라 위 파일 중 하나에 작성한다. 이 외의 정보가 있을시 사용자에게 보고한다.
- 파일의 숫자 접두사는 문서 표시 순서를 고정하며, 요구사항 ID의 일부로 사용하지 않는다.
- 기존 요구사항을 다른 적용 범위의 문서로 이관할 때는 이력 보존을 위해 ID, 상태와 우선순위를 임의로 변경하지 않는다.
- 두 페이지의 동작을 하나의 요구사항으로 묶지 않고 각 페이지에서 독립적으로 검증할 수 있게 분리한다.
- 기존 `brief.md`, `PRD.md`, `common/**`, `welcome/**`는 분류·이관이 끝날 때까지 유지하며, 사용자 승인 없이 삭제하지 않는다.

# 요구사항 종류

- REQ: 기능 요구사항
- NFR: 비기능 요구사항

# 요구사항 상태

- TBD: 아직 결정되지 않음
- DECIDED: 결정 완료
- REJECTED: 채택하지 않음
- SUPERSEDED: 다른 요구사항이나 결정으로 대체됨

# 이름 규칙

- REQ-{영역}-{번호}
- NFR-{영역}-{번호}

예:

- REQ-common-001
- REQ-cases-001
- NFR-common-001

# 작성 규칙

- 하나의 요구사항에는 하나의 요구사항만 적는다.
- 번호는 삭제 후에도 재사용하지 않는다.
- 번흐는 파일마다 001부터 시작한다.
- 파일명 변경 시 요구사항 ID는 변경하지 않는다.
- 생성시에는 상태는 TBD처리한다.

예 :

```txt

# NFR-common-999

- 상태 : DECIDED
- 요구사항 : 필터 버튼 기능


```

# 중복된 요구사항 관련

- common은 모든 화면에서 적용되는 요구사항 또는 기획이다.여기에 적힌 내용은 중복이 되어선 안된다.

```txt
예 :

- 필터를 어떻게 만들것인가? 라는 요구사항
- A화면에서의 필터는 어떻게 만들것인가? 라는 요구사항

- 위의 요구사항과 같이 요구사항이 겹치는 경우는 없어야한다.

```

# common과 화면의 중점

- common은 위와 같이 어떠한 기능에 대해 요구사항을 만든다.
- home,cases.. 등과 같이 화면에 대한건 해당 화면의 기획에 어떤 데이터 필요한지 자연스러운 유도를 할 수 있는 요구사항으로 만든다.
- 아래는 화면에 대한 데이터 요구사항 예시다

```txt

# NFR-example-999

- 상태: DECIDED
- 제목: 시공 사례 필터

## 완료 기준

- 시공 사례 필터에는 시공 사례에 모든 데이터가 나와야한다.
- 시공 사례의 데이터의 분류는 2가지로 되어있다.

```
